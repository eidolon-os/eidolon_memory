# 抽取层的架构级修复方案（待 review）

写于 2026-08-09。依据是 `reports/memory_quality_20260809_082825` 这一次 90 轮实测，
文中每个数字和每个实体 id 都是从那次运行的图里读出来的，不是举例。

---

## 一句话根因

**抽取器是一个无状态的、逐轮的 LLM 调用，却被要求产出全局一致的标识符、并识别"这条事实
取代了哪条旧事实"——而这两件事都取决于它从未被给看的那张图。**

其余全部现象都是这一条的推论。特别地：**这次的错误输出几乎全部是 prompt-compliant 的**，
所以"把 prompt 写得更严"不是方案。

- 第 2 轮"我妈张丽" → `mother:张丽`。第 28 轮"我妈搬家了"没提名字，按 prompt
  第 79 行的规则，`mother` **就是正确答案**。两个 id 都对，指的是同一个人。
- `self -[attended]-> 送铁锤到_mother_处` 不是模型走神，它照抄的是 prompt 第 106 行
  的示例 `{subject:"self", predicate:"attended", object:"陪 mother 去医院"}`。
- 要模型在第 28 轮说出"这取代了 `mother lives_in 西湖区`"，它必须知道那条三元组存在。
  它不知道。prompt 里所有 invalidation 示例都是**同一轮内的显式否定**（"我现在不喝咖啡
  了"），那种情况旧事实在原文里被重述了，所以无状态也能做。

## 实测出来的三个后果

### 后果一：实体表里 60% 不是实体

89 个 `entity_id`，人工分类后约 35 个是真实体，其余是事件/状态短语被建成了节点：

```
送铁锤到_mother_处          帮_person:小林_兜底未交付的任务
每天早上过一遍_op-3091_进度    入住祇园附近旅馆且步行可达清水寺
make_and_send_osmanthus_lotus_root_annually
日本旅行（京都4天、大阪2天）   西湖区房产挂牌出售中
```

**关系被编码进了节点名。** `送铁锤到_mother_处` 本该是一条边
`self -[gave]-> pet:铁锤`，现在"送"和"给谁"都埋在字符串里，图无法沿着它走。

`kg_entities.entity_type` 这一列存在、schema 里有默认值 `'unknown'`，
**89 个实体全部是 `unknown`**——从来没有任何代码写过它。

### 后果二：同一个东西有多个 id

从这次的实体表里直接读出来的：

| 同一个所指 | 图里的 id |
|---|---|
| 妈妈 | `mother`、`mother:张丽` |
| 爸爸 | `father`、`father:李国强` |
| 妹妹 | `sister`、`sister:李婷` |
| 陈昊的女儿 | `person:念念`、`person:陈昊之女` |
| 星槎项目 | `project:星槎`、`project:星槎项目`、`星槎项目负责人`、`project:星槎_第一版交付` |
| OP-3091 | `project:op-3091`、`op-3091_的负责人`、`closely_monitoring_op-3091`、`每天早上过一遍_op-3091_进度` |
| 出版社 | `place:出版社`、`publishing_house` |
| 恒维医疗 | `company:恒维医疗`、`medical_device_company` |
| 睡不好 | `insomnia`、`poor_sleep`、`sleep_issue` |

最后四行还暴露了一件独立的事：**模型会把对象翻译成英文**，而且不稳定——米氮平写成
`mirtazapine`、合唱团写成 `choir`、桂花糖藕写成
`make_and_send_osmanthus_lotus_root_annually`。所以有用的边挂在 `mother` 上，
而 `mother:张丽` 只有一条 `has_state -> insomnia`。

### 后果三：没有任何东西被"取代"

12 道多跳题的失败分布：**7 题端点实体图里不存在，4 题两端都在但无边相连，1 题
（hop-008）通过了但那道题是我出错了**——查询里写了"我妈"，也就是桥接实体本身，退化成
单跳。**没有一道题在图里存在真正的两跳路径**，所以"图能不能遍历"这次根本没被测到。

6 道失效题里 5 道把当前事实答对了，全部只因为旧事实一起回来而判错。逐条查图：

| 旧 → 新 | 图里的旧值 | 图里的新值 |
|---|---|---|
| 西湖区 → 滨江区 | 只有 `self has_state 西湖区房产挂牌出售中`（事件短语） | `mother lives_in place:滨江区` |
| 舍曲林 → 米氮平 | **没有** | `mother takes_medication mirtazapine` |
| 急诊 → 内科 | **没有** | `person:王芳 works_at place:内科` |
| 实习生 → 转正 | **没有** | `person:小林 achieved 转正` |
| OP-3091 → 星槎 | `person:李总 holds_role op-3091_的负责人` | `person:李总 holds_role 星槎项目负责人` |
| 六月底 → 两周 | `self has_concern 六月底出第一版` | **没有** |

**六次违规全部是 `VIOLATE-vec:`。** 旧文本来自抽屉库而不是图——去 chroma 里查，
"她退休两年了，一直住杭州西湖区那套老房子"、"开了舍曲林，先吃三个月"都还活着，没被归档。

这一点决定了方案的重心：**失效的主战场在抽屉侧，不在图侧。** 只修图的方案在这六道题上
得零分。

## 先对照别人怎么做的（2026-08-09 补，推翻了本文第一版的方案）

本文第一版的方案是我自己推的，没有对照。对照之后**三处是过度设计**，而且我漏了最重要的
一条。证据来自 Graphiti（Zep 的时序知识图谱，agent memory 里做这件事最完整的开源实现）
的源码与 prompt，以及 Mem0 的公开行为。

### Graphiti 的写入管线（五步）

1. **抽实体** —— 逐 episode 无状态，但 prompt 里有一张**明令禁止清单**
   （`graphiti_core/prompts/extract_nodes.py`）：

   > NEVER extract: 代词；抽象概念与情绪（joy, balance, growth, happiness）；泛化名词；
   > **句子片段或从句**（"what you really care about"）；形容词短语；
   > **裸的亲属称谓**（dad, mom, mother, father, sister…）与裸的宠物词（dog, cat, pet）
   > —— "Instead, qualify them with the possessor: extract **'Nisha's dad' not 'dad'**"

2. **实体去重** —— **单独一次 LLM 调用**，把从图里检索到的候选实体作为
   `<EXISTING ENTITIES>` 连同 `candidate_id` 一起给模型，只问一件事："是不是同一个
   real-world object"，返回 `candidate_id` 或 `-1`。**不是把图塞进抽取 prompt。**

3. **抽边** —— 带 `valid_at` / `invalid_at`，从本轮文本判断。

4. **检索失效候选** —— 用**语义检索**在图里找与新边相近的旧边
   （`edge_invalidation_candidate_results`）。

5. **判定矛盾** —— `resolve_edge_contradictions()` 是**纯确定性的时间戳比较，没有 LLM**：
   若候选旧边的 `valid_at` 早于新边的 `valid_at`，就把旧边的 `invalid_at` 设成新边的
   `valid_at`，并盖 `expired_at`。

### Mem0

默认是**加法式**的：新事实写进去，旧的不动，靠检索时的时效/相关性去浮出当前真相。
社区里"语义相近的矛盾事实没有冲突消解"是**公开未解的 issue**。

→ 所以我们 `invalidation 0/6` **不是我们独有的破**，那是这个领域的默认行为；
真正解决它的（Graphiti）用的是**检索候选 + 时间戳比较**，不是让模型去发现取代关系。

## 我漏掉的那一条（最重要，且几乎免费）

`mother` 与 `mother:张丽` 分裂的根因，不是缺合并机制，而是**我们的命名规则本身不是
无状态可满足的**：

> prompt 第 79 行：「妈妈/我妈/老妈」→ `mother`；**若用户提到名字如"张丽"，用
> `mother:张丽`**

第 2 轮提了名字 → `mother:张丽`；第 28 轮没提 → `mother`。**同一个人，两个 id，两次都
合规。** 规则依赖了"本轮是否恰好提到名字"这个偶然事实。

Graphiti 的规则是 **possessor-qualified**：永远写"某某的妈妈"，从不写裸的"妈妈"。
**这条规则在任何一轮都可满足**，因为占有者（说话人）永远在场，与名字是否出现无关。

**改这一行 prompt，整类分裂就没有了，不需要任何合并机制。** 这是本文第一版最大的疏漏：
我为一个本不该存在的问题设计了 L2 的合并账本、规范 id 间接层和可逆合并。

## 修订后的方案（比第一版小很多）

### P1 — 改抽取 prompt 的两条规则（确定性收益最大，成本最低）

1. **命名改成无状态可满足**：亲属/宠物/同事一律带占有者限定（`owner的妈妈` 一类），
   删掉"提到名字才加名字"的条件分支。
2. **加禁止清单**：抽象概念与情绪、句子片段与从句、泛化裸名词不得成为实体。
   同时**删掉 prompt 第 106 行那条把事件当 object 的示例**——它是
   `送铁锤到_mother_处` 这类节点的直接来源，是 prompt 自己教出来的。

预期：89 个实体里约 60% 的事件短语与 `insomnia`/`boredom`/`stress` 一类同时消失，
`mother`/`father`/`sister` 三组分裂消失。**这一步不写一行新代码。**

### P2 — 实体去重做成独立一步（检索候选 + LLM 判同一）

抽完实体后，对每个新实体检索图里名字/向量相近的候选，交给一次小的 LLM 调用判
"是不是同一个"。这替代第一版的 L2 全部机制。

- 覆盖 P1 覆盖不到的：`person:念念` / `person:陈昊之女`、`place:出版社` /
  `publishing_house`（模型翻译造成的分裂）。
- 风险在**过度合并**——把两个同姓的人并成一个比不合并更糟。验收里要放反例。

### P3 — 失效改成"检索候选 + 时间戳比较"，删掉功能性谓词清单

第一版的 L3 要手工声明一张功能性谓词表（`lives_in`/`works_at`/…）。Graphiti 不维护这种
表：它按语义检索出相近的旧边，然后纯用时间戳判定。**后者泛化，前者要人去维护且必然漏。**

我们的 `valid_from` / `valid_to` / `recorded_at` 已经齐了，缺的就是这一步。

### P4 — 抽屉侧的取代（**这一条我们必须自己解决，他们没有对应物**）

这是我们和 Graphiti 的真实架构差异：**他们只有一个存储**（边自带 embedding，图就是检索
对象）；**我们有两个**（抽屉向量库 + 图）。所以"旧边失效"在他们那里等于"旧事实不再被
召回"，在我们这里**不等于**——这次六次违规全部来自抽屉侧，图侧只有 1 组旧值存在过。

所以 P3 的失效必须连带触发抽屉归档。`canonical_facts` 账本里的 `projection_id` 就是
"该归档哪一条"的唯一线索，链路现成且有测试，**缺的只是触发源**。

**排序建议：P1 → 重测 → P3+P4 → 重测 → 视情况再上 P2。**
P1 不写代码，重测一次就能知道它到底吃掉了多少问题；在那之前谈 P2 的规模是没有依据的。

## 这是不是最适合 eidolon 的方案（2026-08-09 二次修订）

上一节把 Graphiti 的做法搬了过来，但没有验证它是否适合**我们的形态**。逐条核对之后，
三处要改，其中一处是目标层面的。

### 一、possessor-qualified 是他们的答案，不是我们的问题

Graphiti 要写 "Nisha's dad" 而不是 "dad"，是因为**他们的图里有很多说话人**——群聊、多用户，
裸的 "dad" 真的有歧义。

我们的 space 是 `(tenant, owner, companion)`，**一个 space 一个 owner**（见
ARCHITECTURE「两层可见性」）。这个库里有且只有一个"妈妈"。所以我们需要的不是占有者限定，
而是**把规则改成无条件的**：要么永远 `mother`，要么永远 `mother:<名>`，**不要"提到名字才
加名字"**。照搬占有者限定，等于给每个 id 加一段我们不需要的消歧噪声。

**结论：P1 的方向对（规则必须无状态可满足），机制要简化。**

### 二、P4 比我写的小得多，因为管道已经通了

`turn_processor.py:447` → `invalidate_exact_canonical_fact()` →
`registration.projection_id` → `backend.get_by_source_turn_id()` → 归档抽屉。
**抽屉侧的失效链路是现成的、接好的、有测试的**，由 `decision.invalidations` 驱动。

所以 P4 不是"造抽屉取代机制"，而是：**让 P3 按时间戳推出来的失效，走同一条
`MemoryIntent` 路径**。范围小一个数量级。

### 三、多跳这个目标本身，证据不足（这条最重要）

这次运行的实测：

| | |
|---|---|
| 返回了任何三元组的题 | 63/96 |
| kg 命中 | 38/96 |
| vec 命中 | 72/96 |
| **只有 kg 命中、vec 没命中** | **4/96** |

那 4 道是：`念念妈妈休产假前在哪工作`、`我妹的孩子叫什么`、`铁锤生病是怎么处理的`、
`我妈刚开始为什么不肯吃药`。

**图的独有贡献是 4%。** 而那 12 道多跳题是**我自己出的**——"送我铁锤的人现在住哪个区"
不是一个语音陪伴产品里真实会出现的说法。我造了一个类目，测出我们不及格，然后为通过它
设计了一套架构。**这是目标层面的过度设计**，比机制层面的更值得砍。

对比之下，失效是**无可争议的真实产品缺陷**：「她住西湖区，也住滨江区」会真的发生在用户
面前，而且是一个陪伴体绝不能犯的错。它也**不主要是 KG 问题**——六次违规全部来自抽屉侧。

### 修订后的取舍

| 做 | 理由 |
|---|---|
| **失效（P3 + 缩小后的 P4）** | 真实产品缺陷；管道已通；`valid_from` 实测 76/76 全部填好，时间戳比较的数据条件已满足 |
| **prompt 两行**（命名无条件化 + 删掉第 106 行那条事件当 object 的示例） | 不写代码；污染物和分裂两类同时收敛 |
| **暂不做：实体去重的 LLM 步（P2）** | 4% 的独有贡献撑不起它；等失效修完重测再看 |
| **暂不做：多跳遍历** | 产品价值未经证实，问题是我自己造的 |

验收标准相应改：**`invalidation ≥ 5/6` 是目标**；`multi_hop` 降级为**诊断指标**，
不作为通过条件。

诚实的边界：4/96 是在**我设计的题目分布**上测的。换一种分布（更多"谁是谁"的问题）会更高。
所以 4% 是一个下界，不是对图的最终判决——但它足以说明"先修失效、后议多跳"这个顺序。

## 不做的事

1. **不放宽 benchmark 或语料。** 这次的守卫和断言都在正确工作，它们是这份诊断的来源。
2. **不把"给模型加告诫"当方案。** 这次的输出几乎全部 prompt-compliant——第 28 轮没提
   名字时 `mother` 就是 prompt 规定的答案，事件当 object 是 prompt 第 106 行的示例。
   要求模型更小心，等于要求它知道它看不到的东西。

   **注意这与 P1 不矛盾。** P1 改的不是"更小心"，是把一条**依赖偶然信息的规则**换成一条
   **任何一轮都可满足的规则**，再删掉一条教坏的示例。前者是告诫，后者是把不可能变成可能。
3. **不维护手工的功能性谓词表**（第一版的 L3）。它要人去补，且必然漏；改用检索候选 +
   时间戳比较。
4. **不把整张图塞进抽取 prompt。** 去重是**单独一步**、只喂检索到的候选，
   这是 Graphiti 的做法，也避免抽取 prompt 无限膨胀和锚定偏差。
5. **不动读路径。** 这次的证据全部指向写入侧。读路径 p95 97.9ms，没有问题。

## 验收标准（先定，再动手）

| 指标 | 今天 | 目标 |
|---|---|---|
| `invalidation` | 0/6 | **≥ 5/6 —— 唯一的通过条件** |
| 实体表中事件短语占比 | ~60% | < 10% |
| 同一人的 id 数 | 2（mother / mother:张丽） | 1 |
| `multi_hop` | 1/12 | 仅作诊断，不作通过条件 |

多跳降级的理由见「这是不是最适合 eidolon 的方案」第三节：图的独有贡献实测 4/96，
而那 12 道题是我自己出的。

顺带要修的坏题：`hop-008` 在查询里写了桥接实体"我妈"，退化成单跳。语料校验器目前
不检查这一点，应当补一条断言：**多跳题的查询文本不得出现桥接实体的任何别名。**

## 与本次已修问题的关系

同一次运行还暴露了两个已经修掉的、不同层次的问题，一并记在这里以免混淆：

- `extensions` 写成散文导致整轮抽取被丢弃 → 已改为按条剥离（`f761a83`）。
- 上游 500 且 `num_retries` 未设 → **未修**，是另一类失败，不在本方案范围内。
